\subsubsection{Executive overview}\label{executive-overview}

This notebook is the main technical report for the final project. The
project studies resilience in EV charging operations under disruptions
on a synthetic A-B-C corridor with two fixed charging stations and
relocatable mobile charging stations (MCS).

The practical question is whether adaptive control of mobile charging
support can reduce queueing pain when charging demand becomes uneven,
capacity drops locally, or service times inflate.

\textbf{Research question}

Can a reinforcement learning policy improve resilience in an EV charging
corridor by dynamically reallocating mobile charging stations to reduce
queue length and waiting time under disruptions?

The intended comparison is between: - a fixed / no-agent baseline, - a
threshold-style rule baseline, - and an RL-controlled mobile-charging
policy.

The current local artifact set supports the full simulator and current
baseline evaluations directly. It does \textbf{not} contain a
current-compatible RL checkpoint for the active 27-feature, 5-action
A-B-C environment, so the quantitative result sections below focus on
the strongest reproducible current evidence and treat older RL artifacts
only as historical context.

    \subsection{1. Simulation goals and design
philosophy}\label{simulation-goals-and-design-philosophy}

The simulator is not intended to be a perfect real-world digital twin.
Its purpose is to create a controlled but operationally meaningful
testbed for resilience questions:

\begin{itemize}
\tightlist
\item
  demand varies over the day instead of staying flat,
\item
  morning and evening peaks create predictable congestion pressure,
\item
  charging stations have finite plugs and stochastic service times,
\item
  disruption events locally damage effective service capacity,
\item
  mobile charging stations can be reallocated, but not instantaneously,
\item
  performance is judged using queueing and waiting-time outcomes under
  disruption.
\end{itemize}

That design choice matters for the project story. Resilience is about
whether the system continues to serve vehicles when local conditions
deteriorate, not only about average utilization on a normal day.

    \subsection{2. Simulation environment}\label{simulation-environment}

The active benchmark is a synthetic line corridor with three cities and
two fixed charging stations:

\begin{itemize}
\tightlist
\item
  City A to City B: 100 km,
\item
  City B to City C: 100 km,
\item
  one fixed station between A and B (\texttt{station\_ab}),
\item
  one fixed station between B and C (\texttt{station\_bc}).
\end{itemize}

Episodes proceed in 5-minute decision steps. Vehicles arrive
stochastically, may choose to charge, join a station queue if necessary,
and start service when a plug becomes free. Mobile charging stations
(MCS) provide extra chargers, but they create a real control problem
because they cannot support both sides of the corridor simultaneously.

Operationally important frictions in the current environment are:

\begin{itemize}
\tightlist
\item
  depot-to-station travel time,
\item
  station-to-station relocation lag,
\item
  return-to-middle behavior,
\item
  recharge delay before an MCS can be reused.
\end{itemize}

Those frictions make the problem spatial and delayed. The controller is
not just ``adding capacity''; it is committing scarce mobile support
under travel and recharge constraints.

    \subsection{3. Problem formulation}\label{problem-formulation}

The control problem is to decide how mobile charging support should be
used to reduce local service pressure under normal demand variation and
under disruptions.

Why is this difficult?

\begin{itemize}
\tightlist
\item
  fixed capacity is static while demand and disruptions are
  time-varying,
\item
  the pressure may be local to AB or BC rather than system-wide,
\item
  MCS deployment is delayed by movement and recharge,
\item
  aggressively using MCS can improve service but also incurs operational
  cost.
\end{itemize}

In this project, \textbf{spatial awareness} means that a good controller
should send more support toward the side of the corridor with higher
local pressure, such as larger queue buildup, higher waiting times,
lower effective local capacity, or a disruption directly affecting that
side.

    \subsection{4. RL agent and method}\label{rl-agent-and-method}

The repository contains two RL paths:

\begin{itemize}
\tightlist
\item
  a custom \texttt{torch\_dqn} / simple DQL learner, useful as a
  lightweight baseline learner,
\item
  an \texttt{sb3\_dqn} path, intended as the stronger final RL
  candidate.
\end{itemize}

Conceptually the RL loop is standard and practical:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  observe the current corridor state,
\item
  choose an action for MCS commitment,
\item
  receive a scalar reward tied to service quality and operating cost,
\item
  improve the action-value function from rollout experience,
\item
  evaluate the learned policy in held-out simulated scenarios.
\end{enumerate}

The important point for this report is not RL theory for its own sake,
but whether the learned controller can improve resilience under
disruption without over-using mobile capacity.

    \subsubsection{What the model does not
know}\label{what-the-model-does-not-know}

    \begin{itemize}
\tightlist
\item
  No exact future arrivals or exact future queue realizations.
\end{itemize}

    
    \begin{itemize}
\tightlist
\item
  No oracle action labels or optimal allocation target.
\end{itemize}

    
    \begin{itemize}
\tightlist
\item
  No foreknowledge of future random disruptions before they begin.
\end{itemize}

    
    \begin{itemize}
\tightlist
\item
  No exact per-MCS battery state-of-charge representation.
\end{itemize}

    
    \begin{itemize}
\tightlist
\item
  No direct remaining-disruption-time feature in the current
  observation.
\end{itemize}

    
    \begin{itemize}
\tightlist
\item
  No explicit demand forecast beyond current local state and disruption
  indicators.
\end{itemize}

    
    This is important for honesty. The agent is not given an oracle forecast
of future arrivals, an exact best action label, or full future
disruption knowledge. It must infer useful reallocations from local
queue/capacity conditions and the currently visible disruption state.

    The intuition is straightforward:

\begin{itemize}
\tightlist
\item
  serve vehicles,
\item
  keep queues and waits low,
\item

  acceptable,
\item
  reward spatially useful MCS placement,
\item

  treat mobile support as free.
\end{itemize}

This also means \textbf{reward and operational performance are related
but not identical}. A policy can reduce queues strongly and still have a
worse reward if it uses too much expensive mobile support.

    \subsection{9. Reward calibration and alternative business
priorities}\label{reward-calibration-and-alternative-business-priorities}

The reward structure can be tuned to reflect different operating
priorities. That is a strength of the framework, not a flaw, as long as
the choice is made explicit.

Examples of business priorities that would justify different weights
are:

\begin{itemize}
\tightlist
\item
  minimizing queue length at almost any cost,
\item
  enforcing a service-level target with limited MCS usage,
\item
  penalizing active MCS-hours heavily because mobile support is
  expensive,
\item
  prioritizing fairness across stations rather than only aggregate
  averages.
\end{itemize}

The repository itself contains evidence that this was treated as a
design knob: there are separate reward-focused configs in the repo, and
the local historical sweep below shows that changing queue and cost
weights materially changes the operating point.

comparison}\label{simulation-rollout-comparison}

The strongest reproducible current comparison is a fixed unseen 5-day
\texttt{test\_id} rollout using the active line-corridor implementation.

baselines that \emph{are} available and current:

\begin{itemize}
\tightlist
\item
  fixed / no-agent (\texttt{mobile\_noop}),
\item
  threshold baseline,
\item
  reactive baseline.
\end{itemize}

This still answers an important resilience question: does adaptive
mobile support materially reduce queueing pain under disruptions, and
how costly is a more aggressive control rule?

    \subsection{16. Missing pieces, failures, and
limitations}\label{missing-pieces-failures-and-limitations}

Several limitations are important for an examiner to see explicitly.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{No current-compatible RL artifact is available locally.} The
  active benchmark can be described precisely, but a final
  RL-vs-baseline quantitative claim is not reproducible from this
  checkout without retraining or recovering the missing
  checkpoint/history.
\item
  \textbf{Current queue-breach metrics are not instrumented as
  service-level targets in the active line corridor.} The exported
  breach columns are therefore zero and should not be over-interpreted.
\item
  \textbf{The simulator is stylized.} It is realistic enough to study
  operational tradeoffs, but it is still a synthetic environment rather
  than a calibrated production deployment model.
\item
  \textbf{Reward sensitivity is real.} The reward sweep and the baseline
  comparisons both show that cost weights change the preferred policy
  substantially.
\item
  \textbf{Spatial response is meaningful but imperfect.} A controller
  can reduce total queues without cleanly matching local deficit
  patterns at every step because demand symmetry, travel lag, recharge
  delay, and cost all matter.
\item
  \textbf{Baselines matter.} The reactive baseline is so strong on queue
  reduction that any future RL claim should be benchmarked against it,
  not only against the no-agent baseline.
\end{enumerate}

    \subsection{17. Conclusion}\label{conclusion}

The project successfully builds a coherent resilience testbed for EV
charging operations under disruption. The simulator captures local
queueing pressure, daily demand structure, multiple disruption types,
and mobile-support logistics in a form that is interpretable and
reproducible.

On the \textbf{current reproducible artifacts}, adaptive mobile support
clearly improves resilience relative to fixed-only operation. The
threshold baseline delivers a strong cost-sensitive tradeoff, while the
reactive baseline delivers the strongest queue reduction at a much
higher mobile-support cost. That distinction is valuable because it
shows why reward design and business priorities matter.

For the original RL research question, the honest answer from this
checkout is partial: the RL formulation is well specified, but a
current-compatible RL checkpoint is missing, so the notebook cannot make
a final defensible claim that the active RL agent outperforms current
baselines. The next concrete step would be to train or recover an SB3
DQN policy for the active 27-feature, 5-action environment and evaluate
it against the threshold and reactive baselines already documented here.
